# Lean のネイティブコンパイルと最適化

Lean 4 は、プログラムを CPU が実行できる機械語へコンパイルできる。通常のネイティブコンパイルでは、Lean コンパイラが最適化した C コードを生成し、C コンパイラが機械語へ変換する。実行ファイルは、生成した機械語を Lean のランタイムや依存ライブラリとリンクして作る。

## C コードを経由するコンパイルの流れ

Lean のコードは、構文解析やエラボレーションを経て、コンパイラが処理する中間表現に変換される。中間表現は、関数、分岐、値の受け渡しなどを最適化しやすい形で表したものである。Lean コンパイラは中間表現に対して複数の変換・最適化を行い、モジュールごとに C ファイルを出力する。

```text
Lean ソース (.lean)
  → 構文解析・エラボレーション
  → Lean の中間表現
  → Lean コンパイラによる変換・最適化
  → C ソース (.c)
  → C コンパイラによる最適化・機械語への変換
  → オブジェクトファイル (.o)
  → Lean ランタイム・依存ライブラリとのリンク
  → ネイティブ実行ファイル
```

Lean の処理は、ソースの構文を一つずつ C の構文に置き換えるだけの変換ではない。C を生成する前に、関数呼び出しやデータの扱いを Lean 側で最適化する。さらに、生成した C コードに対して、C コンパイラ側でも最適化を行う。実際に適用される最適化は、コードの形やコンパイル設定によって変わる。

通常は [Lake](elan_lake.md) が C の生成、コンパイル、リンクを管理する。実行ファイルの標準的な保存先は `.lake/build/bin/`、生成した C コードなどの保存先は `.lake/build/ir/` である。

参照：[公式リファレンス：エラボレーションの結果と C コードの生成](https://lean-lang.org/doc/reference/latest/Elaboration-and-Compilation/#elaboration-results)、[Lake](https://lean-lang.org/doc/reference/latest/Build-Tools-and-Distribution/Lake/)。

### インポート用ファイルとネイティブ生成物の違い

`.olean` は、宣言や環境の情報を保存し、別の Lean モジュールからの `import` に使うファイルである。ネイティブ実行ファイルや機械語のオブジェクトファイルとは用途が異なる。Lean ファイルの型検査や証明の検査を行うことと、独立した実行ファイルを作ることも区別する必要がある。

## Lean 側の代表的な最適化

Lean コンパイラは、関数や純粋な計算の構造を利用して、呼び出し、重複した計算、メモリ管理などのコストを減らす。代表的な最適化には次のものがある。

| 最適化 | 処理の内容 | 例・効果 |
| --- | --- | --- |
| インライン化 | 関数の呼び出し箇所に関数本体を展開する | 小さな関数の呼び出しを省き、展開後の式をさらに簡約できる |
| 関数の特殊化 | コンパイル時に分かる特定の引数に合わせた関数を生成する | 関数を引数として受け取る処理に、具体的な関数専用の実装を用意し、間接的な呼び出しなどを減らせる |
| 定数畳み込みと式の簡約 | 値が分かる演算を事前に計算し、簡約可能な式を置き換える | `Nat` の `2 + 3` を `5` に置き換え、実行時の加算を省く |
| 不要なコードや分岐の除去 | 使われない値の束縛や、到達しないことが分かる分岐を除く | 分岐条件やコンストラクターが分かる場合に、不要な分岐を消せる |
| 共通部分式の除去 | 同じ純粋な式の計算結果を再利用する | 同じ引数に対する同じ計算を、繰り返し行う必要を減らす |
| 参照カウント操作の最適化 | 引数を借用できるか推論し、参照カウントの増減を減らす。また、同じ値への複数の増加操作や減少操作をまとめる | 呼び出し後にも使う値について、不要な参照カウントの増加・減少を省ける |
| メモリ領域の再利用 | 不要になる値の領域を、適合する新しい値の格納先として利用するコードを生成する | リストの変換などで、条件を満たせば新規割り当てを減らせる |

最適化は相互に作用する。たとえば、インライン化によって関数の内部が呼び出し側に現れると、定数畳み込みや不要な分岐の除去が可能になることがある。表の効果は、すべての呼び出しや式で必ず得られるという保証ではない。

参照：[公式 API：コンパイラの変換・最適化パス](https://lean-lang.org/doc/api/Lean/Compiler/LCNF/Passes.html)、[定数畳み込み](https://lean-lang.org/doc/api/Lean/Compiler/LCNF/Simp/ConstantFold.html)、[共通部分式の除去](https://lean-lang.org/doc/api/Lean/Compiler/LCNF/CSE.html)。

### インライン化と特殊化の具体例

`@[inline]` は、コンパイラに関数のインライン化を指示する属性である。次の例では、`addOne` の呼び出し箇所に `n + 1` を展開できる。

```lean
import Init

@[inline] def addOne (n : Nat) : Nat := n + 1

def addTwo (n : Nat) : Nat := addOne (addOne n)

#eval addTwo 10
```

`addTwo` の計算結果は `12` になる。インライン化は、呼び出しの結果を保ちつつ、実行コードで関数本体を扱う方法を変える。

`@[specialize]` は、関数の特殊化を促す属性である。次の `applyTwice` は関数 `f` を引数として受け取る。`incrementTwice` では具体的な関数 `fun n => n + 1` が分かるため、その関数に合わせた特殊化が可能になる。

```lean
import Init

@[specialize] def applyTwice (f : Nat → Nat) (n : Nat) : Nat :=
  f (f n)

def incrementTwice (n : Nat) : Nat :=
  applyTwice (fun n => n + 1) n

#eval incrementTwice 10
```

`incrementTwice` の計算結果も `12` になる。インライン化は呼び出し箇所への展開、特殊化は特定の引数に合わせた実装の生成という違いがある。

`#eval` は計算結果を確認するためのコマンドであり、上の出力だけではネイティブコードでどの最適化が適用されたかは分からない。

参照：[公式 API：インライン属性](https://lean-lang.org/doc/api/Lean/Compiler/InlineAttrs.html)、[特殊化属性](https://lean-lang.org/doc/api/Lean/Compiler/Specialize.html)。

### メモリ管理の最適化の条件

Lean のランタイムは参照カウントでメモリを管理する。参照カウントは、値を参照する箇所の数を記録する仕組みである。借用の推論によって、呼び出し先が引数の参照カウントを減らさないと分かれば、呼び出し元で値の寿命を保つための余分な増加操作を省ける。

メモリの再利用では、実行時の共有状態も関係する。コンパイラが再利用を試みるコードを生成しても、値がほかから参照されていれば、その領域を自由に上書きできない。必要な参照が一つだけで、領域の大きさや配置などが適合する場合に、元の領域を新しい値に利用できる。Lean の純粋なコードでも、元の値を必要とする参照を壊さずに内部のメモリ操作を効率化できる。

参照：[公式リファレンス：参照カウント](https://lean-lang.org/doc/reference/latest/Run-Time-Code/Reference-Counting/)、[公式 API：借用の推論](https://lean-lang.org/doc/api/Lean/Compiler/LCNF/InferBorrow.html)、[メモリ再利用の挿入](https://lean-lang.org/doc/api/Lean/Compiler/LCNF/ResetReuse.html)。

### 証明の消去

コンパイラは、実行時に不要な証明も消去する。たとえば、条件の証明を伴うデータでも、証明項そのものを実行時データとして保持する必要はない。証明の正しさの検査と、実行に必要なデータの生成は役割が異なる。証明の消去と[証明の無関連性](../foundations/type_system.md#5-証明の無関連性)にも関係がある。

## 開発中の LLVM バックエンド

LLVM バックエンドは、Lean の中間表現から、C ソースを介さずに LLVM ビットコードを生成するコンパイラの出力処理である。LLVM ビットコードは、LLVM が扱う中間表現のバイナリ形式である。Lean コンパイラが `.bc` ファイルを出力し、機械語への変換とリンクを経て実行ファイルを作る。

LLVM バックエンドの実装は Lean 本体に取り込まれているが、通常の C 言語経由を置き換える標準バックエンドにはなっていない。標準化に向けた作業は `LLVM MVP` というマイルストーンで管理されており、LLVM バックエンドを既定にして Lean 自身のコンパイルにも使う課題は未完了である。この課題には、現在作業を予定していないことを示す `P-low` ラベルが付いている。

LLVM バックエンドは、本体に実装された追加のコンパイル経路であり、標準採用に向けた課題が残っているという位置づけである。利用には LLVM 対応を有効にしてビルドされた Lean が必要になる。

```text
Lean ソース (.lean)
  → Lean の中間表現・変換・最適化
  → LLVM ビットコード (.bc)
  → 機械語への変換
  → オブジェクトファイル (.o)
  → リンク
  → ネイティブ実行ファイル
```

「LLVM で直接ネイティブコードを生成する」という説明の「直接」は、C ソースの生成を省くという意味である。中間表現やリンクの段階まで省略するわけではない。Lake には C と LLVM のバックエンドを選ぶ設定と、ビットコードからオブジェクトファイルを生成するビルド対象がある。

### LLVM バックエンドの利用条件

LLVM バックエンドの利用には、LLVM 対応を有効にしてビルドされた Lean が必要である。Lake の設定を変更するだけで、LLVM 対応を持たない Lean に機能を追加することはできない。利用中の Lean が提供する機能は、次のコマンドで確認できる。

```sh
lake env lean --features
```

LLVM バックエンドが実装されていることと、標準配布で有効になっていることは区別する必要がある。利用可否は対象のツールチェーンで確認する。

なお、標準配布に同梱される C コンパイラは Clang であり、Clang 自体も内部で LLVM を使う。C 経由と LLVM バックエンド経由の違いは、Lean が C ソースを生成するかどうかにある。

参照：[公式リファレンス：Lake のバックエンド](https://lean-lang.org/doc/reference/latest/Build-Tools-and-Distribution/Lake/#Lake.Backend)、[Lean のコマンドライン](https://lean-lang.org/doc/reference/latest/Interacting-with-Lean/)、[ビルドツールと配布](https://lean-lang.org/doc/reference/latest/Build-Tools-and-Distribution/)。
