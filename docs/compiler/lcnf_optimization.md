# Lean コンパイラの最適化パスの拡張

Lean では、コンパイラに独自の最適化処理を追加できる。最適化パスは、コンパイルの途中でプログラムを変換し、計算結果を保ちながら不要な処理などを省く一段階の処理である。自分で作ったパスを標準の最適化の前後に組み込むことで、特定の関数やデータの性質に合わせた変換を実行コードへ反映できる。

たとえば、引数をそのまま返す関数への呼び出しを、引数そのものへ置き換える最適化を追加できる。追加する処理では、コンパイル中のプログラムを受け取り、必要な箇所を変換して返す。拡張を Lean のモジュールとして定義しておけば、インポート先のコンパイルにも適用できる。

## 独自の変換処理の作成と登録

最適化の追加には、プログラムをどう変換するかを定義する作業と、その変換をコンパイルのどの位置で実行するかを指定する作業がある。

1. コンパイル中のプログラムから、書き換えたい計算や呼び出しを探して変換する関数を作る。
2. 変換する関数に、処理の名前や対象となるコンパイル段階を添えて、一つの最適化パスにまとめる。Lean では、このパスを `Pass` 型の値として作る。
3. 標準の最適化の前後など、パスを組み込む位置を指定する。Lean では、組み込み方を `PassInstaller` 型の値として作り、その定義に `@[cpass]` を付けて登録する。

`Pass` は変換処理そのものを表し、`PassInstaller` はコンパイラの処理列への組み込み方を表す。`@[cpass]` を付けるのは、組み込み方を定義した宣言である。

## 最適化の対象となる中間表現

Lean コンパイラは、ソースコードを機械語へ変換する途中で、関数呼び出しや分岐などを処理しやすい形に組み直す。このコンパイル途中のプログラムの表現を中間表現と呼ぶ。独自の最適化パスも、中間表現を調べて変換する。

Lean の最適化に使われる中間表現の一つが LCNF（Let-normalized Compiler Normal Form）である。途中の計算結果を `let` で名前に結び付け、関数呼び出しや分岐、返却を明示する。たとえば、引数をそのまま返す関数を `identityNat` とすると、`identityNat n + 1` は、おおむね次の形になる。実際の初期変換では型クラスの操作なども含まれる。

```text
let x := identityNat n
let one := 1
let result := Nat.add x one
return result
```

LCNF のデータ型と変換処理は、`Lean.Compiler.LCNF` という名前空間にまとめられている。一つの宣言は `Decl`、宣言の本体に含まれる計算や分岐は `Code` という型で表す。変換パスは宣言や本体の値を調べて組み立て直す。

変換する関数は、コンパイラの環境や変数の情報を扱える `CompilerM` というモナドで実装する。

## 変換と登録の短い例

引数をそのまま返す関数 `identityNat` への呼び出しなら、次のように引数への参照に置き換えられる。

```text
Before: let x := identityNat n
After:  let x := n
```

変換する関数を、一宣言ずつ実行するパスにまとめる補助関数が `Pass.mkPerDeclaration` である。たとえば、宣言を変換する関数 `transformDecl : Decl .pure → CompilerM (Decl .pure)` を定義しておけば、パスの作成と登録は次の形になる。

```text
meta def customPass : Pass :=
  Pass.mkPerDeclaration `customOptimization .base transformDecl

@[cpass] meta def installCustomPass : PassInstaller :=
  PassInstaller.installBefore .base `simp (fun _ => customPass)
```

`.base` は型の情報が残る初期の段階、`simp` は標準の簡約パスの名前である。登録によって、最初の簡約パスの直前に独自の変換が実行される。変換する関数では、書き換えたい呼び出しを探し、対象の関数と引数が条件に合う場合だけ変更する。

## 変換で扱うデータと設定項目

コンパイル中の宣言や計算を調べるために、LCNF は対象ごとのデータ型を提供する。表の `pu` は中間表現の種類を指定する引数であり、初期の段階では `.pure` を指定する。

| 表す対象 | Lean の API |
| --- | --- |
| コンパイル中の宣言。名前、引数、型、本体などを保持 | `Decl pu` |
| LCNF のコードを持つ宣言の本体 | `DeclValue.code` |
| 外部実装に対応する宣言の本体 | `DeclValue.extern` |
| `let`、局所関数、join point、分岐、返却など | `Code pu` |
| 一つの `let` 束縛と、その右辺 | `LetDecl pu`・`LetValue pu` |
| 変数、型、消去された値などの引数 | `Arg pu` |
| 局所宣言の情報やコンパイラの環境を扱うモナド | `CompilerM` |

join point は、分岐の合流先などを表す局所的な処理のまとまりであり、`Code.jp` で定義し、`Code.jmp` で移る。

### コンパイル段階ごとの表現

コンパイルが進むにつれて、型の情報を消去し、メモリ管理などの実行時の操作を明示する。LCNF では段階を `Phase` という型で区別する。

| 主な特徴 | 段階の指定 | 中間表現の種類 |
| --- | --- | --- |
| 型や多相性の情報を利用する初期の変換・最適化 | `.base` | `.pure` |
| 実行に不要な型の情報を消去し、実行時の型表現へ寄せた変換・最適化 | `.mono` | `.pure` |
| オブジェクト操作、参照カウント、メモリ再利用などを明示する段階 | `.impure` | `.impure` |

`Purity.pure` と `Purity.impure` は、パスが扱う中間表現の種類を表す。`IO` を使うソースプログラムも `.base`・`.mono` を通るため、`Decl .pure` を受け取っただけでソースプログラムに副作用がないと判断することはできない。

### パスの設定項目

宣言の配列全体を扱う変換や、入力と出力で段階が変わる変換では、`Pass` の設定項目を直接指定できる。

| 設定する内容 | `Pass` のフィールド |
| --- | --- |
| パスの名前 | `name` |
| 入力のコンパイル段階 | `phase` |
| 出力のコンパイル段階 | `phaseOut` |
| 宣言の配列を受け取り、変換後の配列を返す関数 | `run` |

通常の段階を変えない最適化では、`phaseOut` は既定値の `phase` のままでよい。

## 標準の処理列への挿入位置と適用範囲

パスの挿入位置は、変換が必要とする情報と後続の処理に合わせて選ぶ。

| 組み込み方 | `PassInstaller` の操作 |
| --- | --- |
| 指定したパスの直前へ追加 | `installBefore phase name f occurrence` |
| 指定したパスの直後へ追加 | `installAfter phase name f occurrence` |
| 指定したパスを置換 | `replacePass phase name f occurrence` |
| 対象のパス配列の末尾へ追加 | `installAtEnd phase pass` |

`f` には対象の既存 `Pass` が渡される。例の `fun _ => customPass` は既存パスの値を利用せず、追加するパスを返す。`occurrence` は同名のパスのどの出現を選ぶかを表す番号で、既定値は `0` である。標準の `simp` は複数回実行されるため、名前に加えてフェーズと出現番号も必要になる。指定した対象が見つからなければ登録時にエラーになる。

段階の変換や宣言の保存もパスに含まれるため、`installAtEnd` で末尾に追加すれば常に安全というわけではない。たとえば `.base` の末尾には `.mono` への変換がある。`.base` の表現を必要とするパスは、その変換より前に置く。

また、Lean 4.35.0-rc3 では、局所関数をトップレベルの関数へ移す処理（ラムダリフティング）の前後で、`.mono` の処理列が分かれている。処理列を管理するデータ型が `PassManager` である。`PassInstaller` の `.mono` に対する通常の操作が変更するのは、前側の `monoPasses` である。後側の `monoPassesNoLambda` にあるパスを名前だけで指定しても挿入できない。

登録したパスは、その後にコンパイルされる宣言へ適用される。すでにコンパイル済みの宣言をさかのぼって変換することはない。拡張を別モジュールへ分けて `import` すると、登録情報も読み込まれ、インポート先のコンパイルへ反映される。`local` や `scoped` な `cpass` 登録はできない。

## 変換前後の動作の一致とバージョンへの依存

最適化では、処理を省いた後も元のプログラムと同じ結果や副作用を保つ必要がある。書き換え規則には、対象の関数、型、引数の数、計算の意味が合う条件を明示する。恒等関数の例なら、対象の関数への一引数の呼び出しだけを変換する。任意の一引数関数を同じように変換すると、結果を変えてしまう。

独自パスは実行コードを変えるが、Lean のカーネルが検査する論理上の定義を書き換えない。通常の型検査や証明の成功だけで独自最適化の正しさを保証できない。`set_option compiler.check true` で中間表現の整合性検査を有効にし、`trace.Compiler.init` と `trace.Compiler.saveBase` で変換前後の表示を確認できる。整合性検査は動作の一致まで証明するものではないため、対象となる入力や分岐での実行結果も確認する。速度の改善を判断する場合には、呼び出し除去の確認とは別に測定も必要になる。

LCNF のデータ型やパスの登録機構は、コンパイラ内部の API である。パスの型や登録方法は Lean 4.35.0-rc3 に対応する。Lean を更新するときは、型やコンストラクターだけでなく、パスの順序、フェーズ、保存位置も確認する必要がある。
