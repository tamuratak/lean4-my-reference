# Lean 日本語リファレンスのレビュー

読者が Lean を理解し、例を実際に使えるかという観点で記事を確認する。ユーザーの提案や既存の説明を正しいと仮定せず、文章と一次資料を照合する。

## 対象と基準

- 対象リポジトリの `AGENTS.md` と、対象記事に適用される配下の指示を読む。現在のユーザー指示を優先する。
- ユーザーが指定した記事・差分を対象とする。差分レビューでも、前後の段落や関連する見出しを読み、記事全体との整合を確認する。対象が未指定なら変更記事を確認し、候補がない場合に対象を尋ねる。
- 通常の記事は `rcases_example.md`、`docs/mathlib/` の数学記事は `mathlib_deriv_example.md` を説明の形式と量の基準にする。基準記事も、表記違反や技術的な誤りの免除規定にはしない。
- レビューのみ実行する。記事を編集しない。

## 編集指示と作業記録の混入

執筆・編集の指示は、記事を作る際の判断基準として適用し、その基準を守ったことの説明に置き換えて本文へ書かない。「ご指示に従って」などの露骨な応答だけでなく、自然な説明文の形をした執筆方針・分類方針・検証手順も点検する。会話を知らない読者に通じる文でも、説明対象が Lean ではなく記事の作り方になっていれば混入の候補である。

### 混入の典型例

- 説明形式・作業範囲の宣言（「参照例に合わせて……の順で説明する」「今後の別の課題として扱う」など）。指定された形式は記事の構成で実現し、従ったことの説明を本文に加えない。
- 編集上の分類・配置の宣言（「このディレクトリの直下に置く」「提供元で一覧を分ける」など）。分類を守るための宣言と、操作の意味・提供元の説明を区別する。
- 例の書き方・検証処理・検証結果（インポートや `text` ブロックの扱い、成功件数など）。完成例の書き方や検証スクリプトの内部処理、作業情報を Lean の解説として繰り返さない。
- 参照方針の遵守の宣言（「公式リファレンスと公式 API に限定する」など）。適切なリンクを実際に付ければよく、方針に従ったことを本文で説明しない。

### 文脈に基づく判定

- 本文、導入、一覧ページの前置き、末尾の節にも目を通し、執筆者やレビュー担当者向けの情報がまとまっていないかを確認する。
- 依頼文や `AGENTS.md` と意味を照合し、指示を言い換えただけの文も対象とする。特定の語句の検索だけで確認を終えない。
- 説明の予定、執筆順、掲載しない内容などの自己説明が、対象そのものの説明の代わりになっていないかを確認し、対象の意味を直接説明する修正案を示す。
- 指示は本文の内容で実現する。インポートの明示にはコード内の `import`、概念と表現の対応には対応表、提供元の区別には適切な分類で応える。
- 操作の提供元、必要なインポート、数学的な成立条件、バージョンによる挙動の違いなど、Lean を使うために必要な情報は残す。技術説明と編集上の分類理由が一文に混在する場合は技術説明を残す。
- 例を実行するための条件と執筆者の検証手順を区別する。バージョン名や `import` の言及自体は混入としないが、検証環境を報告するだけの文は指摘する。
- 作業報告や検証結果はチャット、必要に応じて `memo.md` に書き、解説記事に作業報告用の節を作らない。

## 導入と注意の順序

記事や節の冒頭で、説明対象の意味・用途・基本的な挙動を肯定形で説明しているかを確認する。
A を説明するのに最初に「AはBではない」という説明から始めない。
混同しやすい記法との違い、制約、例外などの注意は、基本説明や具体例の後で、独立した段落や内容を示す見出しによって見つけやすく示す修正案を出す。必要な注意を削除したり、他の説明に埋もれさせたりしない。

## 指示語と参照先

「これ」「それ」「この」「その」「あの」「どの」「ここ」「そこ」「こう」「そう」「これら」「それら」などの使用箇所を、周辺の文やコードと併せて読む。

- 参照先が複数考えられる、遠い、明示されていない場合は指摘する。特に複数の型・式・仮定・ゴールが並ぶ説明を確認する。
- 「これは〜である」「この場合」などが、直前の内容を名前で呼べば済むのに使われ、読者に参照先の復元を強いていないかを確認する。
- 原則として型名、式、仮定名、操作名、条件などに置き換える修正案を示す。例：「これは仮定を分解する」なら、文脈に応じて「`rcases h` は仮定 `h` を分解する」とする。
- 参照先が明確で、繰り返しを避けて理解を助ける指示語は許容する。疑問文の「どの型か」なども一律に削除しない。文字列中の一致や語の一部分は指示語と決めつけない。
- レビューの指摘には、曖昧な参照先や不要な読み戻しなど、読者への具体的な影響を添える。

## 技術的な正確さと根拠

説明の中心となる主張を、公式リファレンスマニュアル・API と実装で裏付ける。疑わしい文だけでなく、記事の結論を支える定義や成立条件も確認する。

- `lean-toolchain`、Lake の依存設定、必要に応じて `lake-manifest.json` を読み、記事が対象とする Lean・ライブラリのバージョンを把握する。
- 利用可能なローカル資料を優先する。この環境では `/Users/tamura/src/github/lean4`、`/Users/tamura/src/github/lean-reference-manual`、`/Users/tamura/src/github/mathlib4` が候補。固定パスの存在を前提にせず、リポジトリの `.lake/packages/` や利用可能な配置も確認する。
- チェックアウトのコミット・タグや依存のリビジョンを照合する。資料の版が異なる場合は、同じ挙動だと決めつけない。対象版の資料が得られなければ未確認の範囲を報告する。
- 宣言名・構文名を `rg` で検索し、型、定義、定理の仮定、関連する実装を読む。`.lake/` の検索は原則 `-g '*.lean'` に絞り、`*.ilean` と `*.olean` を除外する。
- tactic の説明では、使用前後の仮定・ゴール、生成される分岐、名前や依存関係の扱いを確認する。型・関数・数学概念の説明では、引数、戻り値、暗黙引数、型クラス、成立条件、条件を満たさない場合の値や挙動を確認する。
- 数学記事では、数学と Lean の対応が正しく、存在や微分可能性などの条件を落としていないかを確認する。値を返す定義と、その値が数学的な意味を持つことを主張する命題を区別する。
- 必要な仮定を外した例や、説明が適用されない境界条件も、主張の強さに応じて確認する。成功例が一つ通るだけで一般的な説明を正しいとしない。
- Web の確認が必要なら公式資料を参照する。内蔵ブラウザやネットワークコマンドが使えない場合は利用可能な検索・閲覧ツールを使う。取得できない資料を読んだことにしない。
- 記事の参照リンクは [公式リファレンスマニュアル](https://lean-lang.org/doc/reference/latest/) または [公式 API](https://lean-lang.org/doc/api/) の該当項目へのリンクとし、ソースコードへのリンクを追加しない。レビューの根拠としては、確認したローカルソースのパス・行番号を示してよい。

## 数学表記と言語

- 解説中の数学記号・数学字体は LaTeX コマンドを使う。例えば数式は `$\alpha$`、`$\forall$`、`$\in$`、`$\mathbb{R}$`、`$\mathbf{x}$`、`$\mathcal{F}$` とし、Unicode の数学字形を直接書かない。
- Lean コード、インラインの Lean 式・識別子、Lean の状態表示では実際の構文を保つ。Lean の `∀`、`∈`、`ℝ` などを LaTeX に置き換えない。バッククォート内でも、Lean の構文ではなく数学の説明なら数式表記に直す。
- チャットと解説は日本語、コード内のコメントは英語とする。
- 特別な理由のない `**` による強調がないかを確認する。

## タイトルとセクション見出し

- 記事タイトルと各セクション見出しが名詞句であるかを確認する。「仮定を分解する」は「仮定の分解」、「等式を証明する」は「等式の証明」のようにする。構文名や API 名だけの見出しも許容する。
- 語尾だけで合否を判定しない。名詞句として自然で、節の中心となる対象・操作・条件を的確に示すかを確認する。
- 節の内容より広すぎる見出し、実際の説明と異なる見出し、隣接する節を区別できない見出しを指摘する。「基本」「補足」なども、具体的な対象を示した方が内容を見つけやすい場合は修正案を示す。
- 見出しだけでなく、本文側の説明不足や節の分割が原因でないかを判断する。本文と対応しない名詞への置換だけで修正を済ませない。

## レビュー結果

指摘は重要度順に、日本語で報告する。内容の誤り、説明の不足、表現・方針上の問題を区別し、単なる好みを不具合として断定しない。

- 各指摘に対象のファイル・行番号、該当表現、問題と読者への影響、根拠、必要な範囲の修正案を添える。技術的な指摘では、一次資料の該当箇所や再現結果を示す。
- 確認済みの問題と、資料不足などによる未確認事項を分ける。推測だけの誤りを確定した指摘にしない。
- 問題が見つからなければその旨を述べ、実際に確認した対象、例の検証結果、残る制約を短く報告する。未確認箇所があるのに全面的な正確さを保証しない。
- 修正した場合は、主な変更と対象記事の検証結果をチャットで報告する。レビュー結果や作業履歴を解説記事に書き戻さない。
